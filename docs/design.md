# 基本設計・要件

[設計書一覧](README.md)

作成・改訂日：2026-09-22。状態：設計。具体的なAPI名や実装構造は案である。

## 1. コアの定義

**コアは、ユーザーが指定した条件でWebを検索し、画像・テキスト・動画・統計／数表を取得する。フィルターは追加機能であり、コアに必要な機能ではない。**

```text
検索要求 → 検索 → 候補・取得先の解決 → 取得 → データ・取得元の記録 → 取得結果
```

これだけで一つの処理として完了する。検索後・取得後に必ず分類器や選別器を通す構成にはしない。取得結果を保存・閲覧・出力するために、スコア、採用判定、選別版を生成する必要はない。

停止、再読み込み、ブラウザ開き直し、取得間隔、予算、保存、出典・失敗の記録は、この検索・取得を成立させる基盤である。用途別の内容評価とは区別する。

最小構成でも選択した検索・取得アダプターは必要である。一方、解析モデルやフィルター、選別用のデータベース構造はコアの必須依存にしない。

## 2. コアと追加機能の境界

| 区分 | 担当するもの | 依存関係 |
| --- | --- | --- |
| コア | 検索要求の実行、検索結果の列挙、データ取得、出典・失敗記録、取得結果の受け渡し | 選択した検索・取得方式に必要な接続部を使う |
| 取得の基盤 | ブラウザ操作、間隔・並列数・予算、停止・復旧、保存・基本出力、公開API | フィルターの存在に依存しない |
| 入力支援 | 自然言語の分解、検索語展開、辞書・タグ変換、自動設定の提案 | 公開された検索要求を生成する交換可能な実装 |
| 任意の検索拡張 | 検索語の追加変換、検索結果の条件評価・選別 | 使用する場合にだけワークフローに追加する |
| 任意の後処理 | 類似度、衣服・キャラクター等の条件判定、品質、重複、利用条件の評価、加工 | 取得データを読み、新しい解析・選別結果を作る |

プラグインという実装方式と、コアに不可欠な役割かどうかは別である。ブラウザ接続部もフィルターも交換可能にできるが、両方を同じ必須依存にしない。

ユーザーが指定したサイト、検索語、期間などを検索先へ渡すことは、検索要求の実行である。初期リンクのドメイン条件も検索範囲の指定として扱う。別の画像分類器で取得データの採否を判定することとは異なる。

### 2.1 必須の設計条件

フィルター未導入・未使用の構成で、コアの起動、検索、取得、保存、基本出力が成立する。解析・選別の実装を読み込まない状態でも検証する。

標準配布物に内製フィルターを同梱しても、それは追加機能の同梱であり、コアへの組み込み必須化ではない。初期プリセットの有効状態は可視化し、ユーザーが変更・取り外しできる。

未使用のフィルターを「解除した」状態とは呼ばない。存在しない判定を「合格」「採用済み」にも変換しない。コアが記録するのは取得の結果である。

検索先やブラウザ自身の非対応・制限・既定動作は別に記録する。コアが選別しないことを、外部サービスがすべての結果を返す保証や、その制限を変更する機能と同一視しない。

## 3. 確定要件

既存の要件IDを維持し、コアの境界をR20〜R22として追加する。

| ID | 要件 |
| --- | --- |
| R01 | 自然言語を分解して検索計画を作り、実行した検索語と条件を表示・編集できる。コアは直接指定された検索要求も受け取る |
| R02 | サイト内検索／サイト指定検索を主要な入口にし、広域検索も選べる |
| R03 | Google、DuckDuckGo、Bing、Yahooの接続プリセットを用意し、複数を同時利用できる |
| R04 | 検索サイトを追加ボタンから登録できる。簡易設定と専用プラグインを区別する |
| R05 | Chromium系・Firefox系を候補にし、ブラウザ接続部を交換できる。検索動作保証はしない |
| R06 | 検索後の初期リンクを対象に、ドメイン条件をチェックボックスと追加登録で指定できる |
| R07 | 自動設定を利用する際、手動優先・自動優先・項目別優先を切り替えられる |
| R08 | 検索フィルターと後処理フィルターを任意に追加・交換し、チェックボックスで使用を切り替える |
| R09 | 内製の品質・関連性・重複・利用条件等の選別フィルターも公開APIを使用し、無効化・取り外し可能にする |
| R10 | データ本体と、発見・取得した場所、使用した条件を記録する |
| R11 | 取得と選別を分離し、追加機能で保存済みデータを異なる条件で選び直せる |
| R12 | 複数検索先への配分は、既定では可能な範囲で均等にする |
| R13 | 簡単プロファイルと詳細設定を分ける。「データ品質優先」は主にデータの豊富さを意味する |
| R14 | 停止、ページ再読み込み、ブラウザ開き直しの操作を用意する |
| R15 | 特に画像取得の時間間隔をユーザー設定にする。並列数や取得予算も設定可能にする |
| R16 | 操作・拡張のAPIを公開する。追加するモデルはローカル実行／外部APIを選べる構造にする |
| R17 | 0.xではテキスト・画像・統計の完成した収集機能は未実装とし、基盤を準備する |
| R18 | 1.0.0でテキスト・画像・統計／数表、1.1.0で動画を取得できるようにする |
| R19 | 既存のブラウザ自動化基盤を流用し、内製簡易ブラウザは将来の交換可能な実装とする |
| R20 | コアの機能的目的を検索・取得に限定し、フィルター未導入の構成を正式にサポートする |
| R21 | コアの設定、完了状態、保存、出力に解析・選別の実行や結果を要求しない |
| R22 | 内製フィルターの標準同梱とコア依存を分離し、追加機能の失敗で取得済みデータを失わせない |

## 4. 検索の入口

| 方式 | 内容 |
| --- | --- |
| `site_native` | 対象サイト自身の検索フォーム、検索URL、提供APIから検索する |
| `site_via_engine` | 選択した検索エンジンを使い、指定サイトの結果を検索する |
| `web` | 選択した検索エンジンで広く検索する |

場所が分かっている場合はサイト内検索・サイト指定検索を先に使い、場所が分からない場合に広域検索を選ぶ。サイト指定では複数サイト、エンジン経由では複数エンジンも選べる。

検索対象サイトと、実際に問い合わせる検索サービスを別に記録する。対象サイトが空のとき、無断で広域検索へ切り替えない。サイトの検索に未対応なら表示し、ユーザーの選択または事前に指定された範囲のフォールバックだけを使う。

保存済みサイト・ブラウザ・取得条件があれば文字入力だけで開始できる。解釈支援を使用しない場合は、入力を検索語としてそのまま使う `literal` 経路を用意する実装案とする。自然文を理解したことにはしない。

サイトの簡易登録には名称、検索URLテンプレート、フォーム操作、結果要素、掲載リンク、データURL、次ページ等を設定する。高度な対応は専用アダプターで行う。URL登録だけでどのサイトでも取得できるとは表示しない。

標準検索エンジンも同じ接続APIを使う。Yahooの地域、実際の接続方式、対応設定は実装時に確認する。非対応の指定は黙って捨てず、要求条件と有効条件を分けて示す。

## 5. 初期リンクのドメイン条件

対象は検索結果から取り出した、最初に開く候補URLである。`all`、`allow_only`、`exclude`の方式を用意する実装案とし、登録済みドメインのチェックと追加登録を行えるようにする。空の許可リストは全許可ではない。

URLのホスト名を解析・正規化して照合し、サブドメインを含めるかを明示する。`example.com.evil.test`を`example.com`として扱うような部分文字列一致はしない。

転送先、画像CDN、ページ付随通信までを、この設定で制限する仕様にはしない。「このサイトだけ」は入口の検索範囲であり、全通信先の保証ではない。最初の候補URLと到達先を別記録にする。

追跡用URLを掲載先へ解決できない場合は不明と記録し、条件を勝手に緩めない。掲載ページから別の掲載ページを巡回する`follow_links`は別設定とし、初期案は無効。画像本体やCDNへの取得とページ巡回を区別する。

## 6. 自然言語・自動設定という入力支援

例：「赤か白のTシャツを着た人物の写真を200枚。商品単体とイラストは不要。背景は問わない。」

解釈支援はデータ種別、対象、属性の係り先、関係、必須・希望・除外条件、AND／OR、未指定、件数の意味を構造化する。元入力、解釈案、実検索語・条件を別保存にする。

同義語、別表記、作品・キャラクター辞書、衣服タグ等の変換を追加できる。モデルだけで曖昧な名前を確定せず、解決根拠や未解決を残す。検索語の言い換えと、希望条件の変更を混同しない。

`manual_first`、`auto_first`、`per_field`を用意し、自動適用範囲もユーザーが設定する。各値の出所を`user`、`model`、`profile`、`default`等で保存する。モデルが自分の適用範囲や使用サービスを増やさない。

条件の理解と画像が条件を満たすかの判定は別である。検索語に「Tシャツ」と含めただけで画像判定器を自動導入しない。希望する画像検証は追加フィルターを使用して行う。

## 7. 構成・依存関係

コア側には操作API、検索・取得スケジューラー、ブラウザ・取得アダプター、保存と基本出力を置く。入力支援と解析・選別は追加機能側に置き、公開APIでコアへ要求を渡す、または取得データを読む。

コアから特定の選別実装・モデル・選別用テーブルへの必須参照を作らない。追加機能はコアのIDやデータを参照できるが、取得項目は解析IDや選別IDなしで成立する。

操作UI、コア、ブラウザを分離する。追加モデルを使用する場合も別ワーカーにし、未起動・故障・取り外しがコアの停止や保存を妨げないようにする。

初期のブラウザ接続候補はPlaywrightとその管理ブラウザとする。Firefoxには対応ビルドを使う。[参考 S1](references.md#s1) 内製簡易ブラウザは既存エンジンに操作UIを付ける範囲で検討し、初期必須にしない。

内製検索は問い合わせの振り分け・結果統合を指し、Web全体の独自インデックスを初期要件にしない。SearXNGは追加接続先の候補であり必須依存ではない。[参考 S5](references.md#s5)

## 8. 追加するフィルター

検索語変換・候補選別と、取得後の解析・選別を処理段階で区別する。チェックボックスの一覧が空でも正常な構成とする。

内製フィルターは標準配布に同梱できるが、追加パッケージとして管理し、公開APIを通す。初期プリセットの有効状態を表示し、ユーザーが追加・交換・無効化・取り外しできる。存在しない実装をコア内の同等処理で置き換えない。

精度、対応範囲、誤除外、未判定を明示する。内製であることや名称を、判定の正しさの根拠にしない。通常の除外は別の選別結果を作る操作であり、元データ削除ではない。

「Tシャツを含む」条件でスカートだけの画像を除く場合、Tシャツとスカートの両方が写る画像まで自動的に不一致にしない。キャラクター、衣服、画風など、揃える特徴と変わってよい特徴は別に扱う。

## 9. UIと変更操作

主画面は入力、データ種別、サイト指定／広域、検索先、ブラウザ、取得プロファイル、開始を中心にする。詳細で取得間隔、上限、初期リンク条件、実検索語を調整する。

追加機能画面で言語解釈やフィルターを登録・使用する。未導入なら「未導入」「未使用」を示し、コアが壊れているような必須設定警告は出さない。使用を指定した拡張が不足している場合は、そのワークフローの未充足として説明する。

取得結果画面は解析・選別なしで閲覧・出力できる。発見・取得成功・失敗・容量等を表示し、採用・除外・保留は選別を実行した結果画面だけに表示する。

実行画面では停止、再読み込み、開き直し、待機理由を表示する。検索設定は版を残す。実行中の取得間隔変更は[runtime.md](runtime.md)に従う。選別条件の変更は取得設定とは別の版にする。

## 10. 範囲・未決定事項

特定サービスのアクセス制限回避、認証の突破、個人の特定・追跡などの専用機能を含めない。取得間隔を設定しても取得・利用の許可を保証するわけではない。ブラウザの権限、端末の秘密情報、保存の整合性などの実行基盤と、任意のデータ選別は別に扱う。

OS、言語、UI、配布、ライセンス、モデル、具体的な既定値は未決定。計画・テストは[ロードマップ](roadmap.md)、契約は[API](api.md)、保存は[データ](data.md)を参照する。
