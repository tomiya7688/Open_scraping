# 基本設計・要件

[設計書一覧](README.md)

改訂日：2026-09-22。状態：設計。具体的なAPI名・値・配置は実装案。

## 1. 完成品ではなく、改変の出発点

**利用者が改変・組み替えによって、自分のソフトを作るための基盤を提供する。** 標準の画面・検索先・部品・処理順序を最終形として固定しない。

Lang to Data by Webは標準構成の用途である。Webを検索し、画像・テキスト・統計／数表・動画を取得する機能は部品の組み合わせで実現する。標準構成をそのまま使うこともできるが、それだけを利用方法にしない。

**コアは部品を接続して流れを実行する。処理そのものは、その目的や種類にかかわらずコアに実装しない。**

前版の「検索・取得がコア」という記述は訂正する。検索もブラウザもダウンロードもフィルターもデータ処理・選別も、最初から同じ境界の外部部品である。

## 2. 責務と依存

| 層 | 実装すること | 実装しないこと |
| --- | --- | --- |
| GUI／CLI | 入力と結果の表示、設定編集、公開API呼び出し | 検索、ブラウザSDK操作、ダウンロード、分類・選別、独自の取得再試行 |
| コア | フロー構造の検証、部品の呼び出し、参照の受渡し、順序・分岐・並列・待機・中断、実行状態 | 検索語推定、サイト解析、HTTP取得、画像判定、集計、保存形式、内容の採否 |
| ホスト／実行環境 | 部品の登録・接続・配送・プロセス管理、権限、状態ストアの接続 | サイトやデータに関する個別判断 |
| 外部部品 | ブラウザ、検索、各フィルター、取得、加工、保存、選別、出力、入力支援 | コアや他部品の設定に対する非公開な変更 |
| 標準配布 | 初期部品、フロー、画面、設定の組み合わせ | 特定部品をコアの固定依存にすること |

「外部」はアーキテクチャ上の境界。同じリポジトリ、同じ配布物、ローカル実行、内製であっても部品として扱う。商用／非商用はこの分類を変えない。

ホストとコアを同じ実行ファイルに置く場合も依存方向を分ける。コアは抽象の呼び出し・状態保存等の契約を使い、具体的なブラウザ・通信・保存バックエンドは構成時に渡す。

## 3. コアへ入れてよいものの判断基準

コアが知るのはノード、接続、操作名、型の識別子、参照、実行状態、期限、資源キー、チェックポイントである。画像や検索エンジンの意味を知る必要はない。

フロー構造の検証や中断通知は実行機構そのもの。どの検索結果を採るか、どの形式で保存するか、どのHTTP応答なら何秒待つかの解釈は具体的な部品処理である。

「どのソフトにも使う」「重要である」「内製なので速く呼べる」は組み込みの理由にしない。共通の具体処理は共通部品・共有ライブラリ・実行環境アダプターとして再利用する。

汎用の待機機構は宣言された時刻と資源キーを扱うだけにする。画像取得の間隔やサイト別キーへの変換は部品が行う。コア内部の実行ジャーナルと、データセット本体を保存する処理も分ける。

処理型の追加のたびにコアの列挙型やベンダー分岐を編集する構成にはしない。共通契約・スキーマを登録し、コアはその接続可能性だけを検証する。

## 4. フロー例と不足部品

標準の収集例は、入力 → 検索部品 → ダウンロード部品 → 保存部品 → 出力部品。ブラウザは必要とする部品へ依存として渡す。

言語解釈、検索フィルター、取得前後のフィルター、加工・選別は必要な位置にノードとして接続する。保存したデータを別フローで選別してもよい。特定の段階数・固定順序をコアに埋め込まない。

部品ゼロでもコアの起動・構成検証はできるが、実処理はできない。検索ノードには対応する検索部品が必要。不足はそのフローの契約不足であり、コアの故障ではない。

GUIのチェックボックスはフローや部品設定の編集を呼ぶ入口。使用していない処理を背後で実行せず、外した後の入出力型が合わなければ差分を示す。

## 5. 合意済み要件

既存IDを維持し、R20の境界を訂正した。R23〜R30がコアの明確化と改変前提の要件。

| ID | 要件 |
| --- | --- |
| R01 | 自然文を分解・編集する入力支援を部品として提供し、直接の検索語入力も扱う |
| R02 | サイト内／サイト指定検索を主要な入口にし、広域検索も選択可能 |
| R03 | Google・DuckDuckGo・Bing・Yahooの接続プリセットと複数同時利用 |
| R04 | サイト追加を簡易設定と専用部品で行える |

| R06 | 検索後の初期リンクを対象にドメイン条件をチェック・追加できる |
| R07 | 入力・設定支援で手動優先、自動優先、項目別優先を選べる |
| R08 | 検索、ダウンロード、後処理のフィルターを追加・交換・選択できる |
| R09 | 内製フィルターも共通APIの部品とし、無効化・取り外し可能 |
| R10 | 本体データと発見・取得元、日時、実条件を記録する |
| R11 | 保存済みデータを再選別でき、除外と元データ削除を分ける |
| R12 | 既定の探索枠配分は、選択した検索先にできるだけ均等 |
| R13 | 簡単プロファイルと詳細設定。品質優先は主にデータの豊富さを意味する |
| R14 | 停止、ページ再読み込み、ブラウザ開き直しを呼び出せる |
| R15 | 特に画像取得間隔をユーザー設定にする。同時数・予算も設定可能 |
| R16 | 操作・部品のAPIを公開。ローカル／外部接続の実装を交換可能にする |
| R17 | 0.xは基盤段階。三種類の収集は未実装・未完成として扱う |
| R18 | 標準構成1.0.0でテキスト・画像・統計／数表、1.1.0で動画 |
| R19 | 内製ブラウザ・検索は既存OSSを共通APIから操作する部品として整備する |
| R20 | コアはフロー実行のみ。検索・取得・フィルターを含む実処理を組み込まない |
| R21 | 取得・保存・直接出力のフローは、選別を必要としない |
| R22 | 同梱部品も外部部品と同じ契約。後段の失敗で保存済みデータを消さない |
| R23 | GUIは表示・入力・API呼び出しのみ。具体的処理を実装しない |
| R24 | ブラウザ・検索・フィルター・取得・保存・処理・選別・出力をすべて部品にする |
| R25 | 標準配布が選ぶ実装と、コアが扱う抽象契約を分ける |
| R26 | GUIなしでも同じAPIで実行・停止・設定・部品操作ができる |
| R27 | 未対応、依存不足、実行失敗、判定不能を区別し、暗黙の代替実行をしない |
| R28 | 利用者が構成・部品・画面を改変して自分のソフトを作ることを主要な利用形態とする |
| R29 | 新しい処理種別や独自フローを、コアの処理別分岐を追加せず導入できる |
| R30 | 標準部品・標準GUI・標準フローを派生構成の必須依存にしない。交換と改変の手順を提供する |

## 6. 検索とサイト指定

検索部品はsite_native（サイト自身）、site_via_engine（エンジン経由のサイト指定）、web（広域）を能力として宣言する案。コアはそれらを検索固有の分岐として持たない。

対象サイトが分かればサイト指定から開始し、分からない場合に広域を選ぶ。対象が空なら無断で全Webへ切り替えない。保存済みの構成があれば文字入力だけで開始できる。

検索対象サイト、実問い合わせ先、検索語、要求条件・有効条件を区別して記録する。非対応条件を黙って捨てない。Yahooの地域や接続方式は採用時に決める。

サイト追加は検索部品の設定スキーマをUIが表示する。検索URLテンプレート、結果要素、ページ送り等の簡易設定と、専用部品を追加する方式に分ける。URL登録だけで全サイトに対応するとは表示しない。

## 7. 初期リンクのドメイン条件

検索後に最初に開く候補URLだけを対象にする。転送先、CDN、ページ付随通信までの制限とは表示しない。最初のURLと到達先を記録する。

allow_only／exclude等の設定とホスト正規化・照合は検索範囲または候補処理部品の責務。コアはその操作を呼ぶだけ。空の許可一覧を全許可にせず、単純な部分文字列一致で別ドメインを認めない。

追跡用URLを解決できなければ不明と記録する。掲載ページからさらに巡回する設定は別にし、画像CDNへの取得とページ巡回を区別する。

## 8. 入力支援・プロファイル

対象、属性の係り先、関係、AND／OR、必須・希望・除外、未指定、件数の意味を解釈部品が分解する。元入力、提案、採用値、実検索条件を別に保持する。

手動優先・自動優先・項目別優先と自動適用範囲を利用者が選ぶ。部品が自分の変更権限や使用サービスを増やさない。辞書・タグ変換も交換可能な部品とする。

検索語を広げることと採用条件を変更することは別。検索語に衣服名が含まれるだけで画像判定器を強制導入しない。

プロファイルは具体的なフローと詳細設定へ展開する部品・テンプレートとして提供する。豊富さ優先の意味を表示し、間隔や固定値を無断変更しない。

## 9. 動作要件は責務を移して維持する

GUIの停止・再読み込み・開き直しは公開APIを呼ぶ。コアは順序・中断・状態を管理し、部品が実通信やブラウザを操作する。画像取得間隔は共有する汎用待機契約と通信部品を組み合わせて実現する。

実際の要求ごとに待機を適用し、ブラウザreopenで予算・待機をリセットしない。解析が遅いだけでブラウザ停止としない。詳細は[runtime.md](runtime.md)。

保存は部品が行い、コアは保存結果の参照を記録する。後段が失敗した場合のフロー状態と、既に保存したデータの存在を分ける。詳細は[data.md](data.md)。

## 10. 改変時の適合条件

別の検索・ブラウザ・保存・選別実装へ交換しても、コアとGUIの具体的処理コードを書き直さずに済むこと。能力差は契約・設定・UIで明示する。

標準構成の画面、部品、フローを使わない派生構成も、同じ契約で動かせること。新しい処理型のためにコアへ処理名のホワイトリストやデータ種別分岐を追加しない。

OS、言語、配布・隔離方式、正式な契約版、モデル、ライセンス等は未決定。改変の道筋は[customization.md](customization.md)、契約は[api.md](api.md)、到達条件は[roadmap.md](roadmap.md)を参照。
