# 基本設計・要件

[設計書一覧](README.md)

作成日：2026-09-22。状態：設計。実装済み機能の説明ではない。

## 1. 製品の目的

**Lang to Data by Web：自然言語から、ユーザーが指定したWeb上のデータを収集・整理する。**

ユーザーはまず短い文章を入力して収集を試す。結果が合わなければ、検索語、検索先、ブラウザ、検索フィルター、取得条件、後処理フィルターを自分で変更する。本体はその作業を可能にする共通基盤であり、用途別の採否を非公開の基準で代行するものではない。

データの場所が分かっている場合は、**サイト内検索・サイト指定検索を第一の入口**にする。場所が分からない場合に広域検索へ切り替える。広域検索を常に先に行う設計にはしない。

## 2. 設計の原則

| 原則 | 意味 |
| --- | --- |
| ユーザーが条件を決める | 検索語、検索先、ブラウザ、検索／後処理の選別条件、実行間隔を編集できる |
| 自動化の範囲も選択可能 | 手動優先、自動優先、項目別の優先順位を設定できる |
| 本体と部品を分離 | ブラウザ、検索先、モデル、解析・選別、出力の実装を交換する |
| 標準機能も同じAPI | 内製の接続部・選別フィルターだけに特別な内部経路を設けない |
| 観測・推定・判断を分離 | 取得できた事実、モデルの推定、ユーザーの採否を混同しない |
| 再選別可能 | 通常の除外は出力対象から外す操作とし、元データの削除とは分ける |
| 成功を偽装しない | 非対応、失敗、未判定、ユーザー除外を区別する |
| 検索成功は保証しない | Chromiumを含め、特定ブラウザ・サイト・検索エンジンでの検索や取得の成功を保証しない |

検索／後処理の選別モジュールと、アプリ自身の権限分離・ファイル保護・停止処理は異なる層である。選別設定の自由と、実行基盤の正しい動作を混同しない。

## 4. 検索の入口

### 4.1 三つの検索方式

| 方式 | 内容 | 前提 |
| --- | --- | --- |
| `site_native` | 対象サイト自身の検索フォーム、検索URL、提供APIから検索する | そのサイト向けの設定またはアダプターが必要 |
| `site_via_engine` | 選択した検索エンジンを使い、指定サイトの結果に限定する | 検索エンジンの対応条件と、初期リンクの照合が必要 |
| `web` | 選択した検索エンジンで広く検索する | ユーザーが広域検索を選んだ場合に使う |

サイト内検索と検索エンジンのサイト指定検索を同一機能と呼ばない。表示する検索先と、実際に問い合わせるサービスの両方を記録する。

サイト指定モードでは単一サイトだけでなく複数サイトをチェックできる。`site_via_engine`では複数エンジンも選べる。サイト自身に検索機能がない／対応アダプターがない場合は、その状態を表示する。別方式への切り替えはユーザーの選択または事前に許可したフォールバックだけで行う。

### 4.2 文字だけで開始する条件

初期画面はサイト指定の入口を中心にする。保存済みのサイト・ブラウザ・設定があれば、検索文だけで開始できる。

サイト指定モードなのに対象サイトが未登録なら、サイトの選択・追加、または広域検索への切り替えを表示する。空の対象サイトを「すべてのWeb」と解釈して実行しない。

### 4.3 サイトの追加

簡易登録には名称、ベースURL、検索URLテンプレート、必要な検索フォーム操作、結果要素、掲載ページへのリンク、画像URL、次ページ操作などを設定する。どの項目が必要かは方式による。

高度な登録では公開APIに従うアダプターを追加する。タグ検索、独自ページ送り、複雑な操作などに対応する。URLを追加しただけで、どのサイトでも正しく抽出できるとは表示しない。

Google等の標準プリセットも同じアダプター仕様で扱う。Yahooの初期地域・サービス識別は未決定とし、日本向けならYahoo! JAPANを明示する。実際に有効な接続方法は実装時に確認する。

## 5. 初期リンクのドメイン設定

### 5.1 適用対象

この設定は、**検索結果から取り出した、最初に開く候補URL**に適用する。画面名は「検索結果から開くドメイン」など、範囲が分かる名称にする。

選択方式は `all`、`allow_only`、`exclude` を用意する実装案とする。登録済みドメインをチェックでき、未登録ドメインを追加できる。`allow_only`で有効な登録がゼロの場合はゼロ件対象であり、制限なしにはしない。

照合はURLとして解析したホスト名に対して行う。大文字小文字、国際化ドメイン、末尾ドットを正規化し、サブドメインを含めるかを各登録で指定する。単純な部分文字列一致は使わない。例えば `example.com.evil.test` を `example.com` と認めない。

### 5.2 範囲外

転送先、画像CDN、ページの付随通信まで、この設定で許可・遮断する仕様にはしない。「このサイトだけ」は候補の入口の制限であり、端末全体の通信先制限ではない。

検索アダプターは可能なら検索エンジンの追跡用リンクではなく、掲載ページへの候補URLを返す。解決できない場合は、解決状態を不明として記録する。勝手に初期リンク条件を緩めない。

掲載ページから別の掲載ページを巡回する範囲は、初期リンク条件とは別の `follow_links` 設定にする実装案であり、既定値は無効とする。元画像へのリンクやCDNへの取得は掲載ページ巡回とは区別する。

## 6. 自然言語の分解

### 6.1 意図と検索語を別に保持する

例：

> 赤か白のTシャツを着ている人物の写真を200枚。商品単体とイラストは不要。背景は問わない。

分解する項目はデータ種別、対象、対象にかかる属性、関係、必須条件、希望条件、除外条件、AND／OR、明示的に問わない条件、未指定項目、取得目標である。

「赤」がTシャツにかかるのか背景にかかるのかを区別する。「200枚」は発見件数・取得成功数・選別後件数のどれかも分ける。

モデルには構造化された検索計画を出力させ、形式を本体で検証する。元入力、解釈、エンジン別に展開した検索語、実際に適用できた設定を個別に保存する。

### 6.2 検索語の展開

同義語、別表記、作品・キャラクター名の辞書、衣服のタグなどを利用可能にする。辞書・タグ変換器も交換可能とする。キャラクター名はモデルの記憶だけで確定せず、曖昧性や解決の根拠を保持する。

広く候補を見つける検索語と、取得後に適用する一致条件は別である。語の言い換えをしたことだけで、元の必須条件が緩和されたことにしない。条件を変更する提案は、選択された自動適用の範囲に従う。

主観語や曖昧な表現は推定であることを示す。ユーザーが指定していない年齢、衣装、人数、画風などを必須条件に固定しない。

### 6.3 手動／自動の優先順位

`manual_first`では手動値を維持し未設定部分を補完する。`auto_first`では自動適用が許可された項目に解釈結果を採用する。`per_field`では項目ごとに指定する。

自動適用可能な範囲そのものはユーザー設定である。モデルが自分の権限を増やしたり、未選択の検索サービスや外部モデルを無断追加したりしない。値には `user`、`model`、`profile`、`default` などの出所を残す。

## 7. ローカル中心の構成

| 部品 | 主な責務 |
| --- | --- |
| 操作UI | 検索入力、設定、候補の確認、停止・復旧操作 |
| ローカルコア | 設定・ジョブ・権限・履歴・保存・APIの管理 |
| 言語解釈プロバイダー | 入力からの条件抽出、検索語展開、変更提案 |
| 検索アダプター | 指定された検索先への問い合わせ、結果と継続情報の取得 |
| ブラウザ接続部 | 起動、ページ操作、再読み込み、終了・再起動、状態通知 |
| 実行スケジューラー | 時間間隔、並列数、検索先への配分、取得上限、停止 |
| 取得・抽出部 | 本体データと出典情報の取得、形式別抽出 |
| 解析・選別プラグイン | 特徴やスコアの計算、ユーザーの条件による選択結果 |
| 保存・出力部 | 元データ、派生データ、選別履歴、マニフェストの保存と出力 |

コアと操作UIの応答を、取得ブラウザの応答や画像モデルの処理完了に依存させない。停止・復旧できるよう、ブラウザやモデルを独立したワーカーで管理する。

### 7.1 既存技術の利用案

最初のブラウザ接続部はPlaywrightと、その管理対象ブラウザを候補とする。Playwrightはブラウザ自動化のライブラリであり、Firefoxには通常配布版とは異なる対応ビルドを使用する。[参考 S1](references.md#s1)

内製簡易ブラウザを追加する場合も描画エンジンを一から作らず、アドレス欄などの操作部分を既存エンジンに付ける。必須の初期実装にはしない。

内製検索は検索計画・振り分け・結果統合の実装を指す。Web全体の独自検索インデックスを初期開発の必須範囲にしない。SearXNGには検索APIがあるため、追加接続先の候補にはできるが必須依存にはしない。[参考 S5](references.md#s5)

言語解釈には小型モデル、画像の意味比較には画像モデルや埋め込みを利用する案とし、特定製品名・モデル・ハードウェアをまだ固定しない。

## 8. 選別の設計

検索フィルターは検索要求や候補URLに、後処理フィルターは取得済みデータに適用する。品質・関連性・重複・利用条件等の標準選別モジュールも、外部製と同じAPIで有効／無効、追加、交換、取り外しを行う。

データの意味に関する解析結果は、まず観測値・推定値として保存する。通常の除外は元ファイルの消去ではなく、その選別結果の出力対象から外すことである。

例えば「Tシャツを含む画像」では、スカートだけの画像は不一致、Tシャツとスカートを着用した画像はTシャツ条件に一致し得る。「スカートが写っていたら除外」という別条件を勝手に追加しない。

LoRA用でも、特定の衣服の一致、特定のキャラクターの一致、画風の一致は分ける。単に多数派に似ていないという理由だけで、正しい全身・横向き画像を落とさない。モデルの信頼度は正解の保証ではなく、誤除外も評価する。

## 9. UIの基本構成

初期画面には自然言語入力、データ種別、サイト指定／広域検索の切り替え、対象サイト、ブラウザ、簡単プロファイル、開始操作を置く。頻用設定を保存して次回は文字入力だけで使えるようにする。

詳細画面には実際の検索語、手動／自動優先、検索エンジン、初期リンクドメイン、検索フィルター、後処理フィルター、時間間隔、同時数、件数・容量上限、モデル設定を置く。追加できる項目には追加ボタンを用意する。

実行画面では、停止・再読み込み・ブラウザ開き直しを操作できる。実行中／待機中／停止処理中／復旧中を区別し、次の取得までの待機理由を表示する。

結果画面では、発見数・取得成功数・一意データ数・採用数・除外数・保留数を分ける。検索先、掲載URL、取得日時、選別理由を参照し、条件を変えて選び直せるようにする。

## 10. 設定を変えた場合

検索語・検索先・モデル・選別条件は履歴を持つ。過去の設定を上書きして履歴を失わせない。

通常の検索条件変更は停止後に新しい設定版を作って実行する案とする。取得間隔などの実行制御を実行中に変更する場合の適用境界は、[ブラウザ・実行制御](runtime.md)で定義する実装案による。

Webで再検索することと、保存済みデータへ同じ選別条件を再適用することを区別する。前者の検索結果が以前と同一になるとは保証しない。

## 11. 実装対象外・未確定範囲

初期設計は汎用の収集・解析・選別を扱うものであり、特定サービスのアクセス制限回避、認証の突破、個人の特定・追跡などの専用機能を含まない。取得間隔の設定だけで、サイトからの取得・利用が許可されたことにはならない。

OS、UIフレームワーク、コア言語、配布方式、ライセンス、具体的モデルと既定値は未決定。外部サイトの挙動、検索可能範囲、規約・利用条件について一律の保証を行わない。

実装上の提案と受入条件は、[API](api.md)、[データ](data.md)、[ロードマップ](roadmap.md)を参照する。
