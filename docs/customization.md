# 改変して自分のソフトを作る

[設計書一覧](README.md)

状態：設計。以下は目指す開発手順と構成案であり、実装済みのSDK・ビルドコマンド・パッケージを示すものではない。

## 1. 想定する利用者

標準のGUIで収集する利用者だけでなく、部品やフローを変更して自分のツールを作る開発者を主要な利用者とする。完成済みのスクレイパーに限定的な拡張点を付けるのではなく、組み立て可能な基盤と、動かし方の参考になる標準構成を提供する。

**具体的な処理は、その種類・重要性・共通性にかかわらず部品へ置く。コアは流れの実行機構に限定する。** 処理を追加するために、まずコアを改造する手順にはしない。

## 2. 変更する場所

| 作りたいもの | 変更対象 | 変更しないもの |
| --- | --- | --- |
| 特定サイト専用の収集ツール | サイト設定、検索部品、フロー | コアの検索実装（存在させない） |
| 別のブラウザを使うアプリ | ブラウザ実装とbinding | フロー実行コア、検索部品の抽象依存 |
| 自分の画像整理ツール | 解析・選別部品、入出力の接続 | コアの画像処理（存在させない） |
| 記事を集めるCLI | CLIクライアント、入力・本文処理・出力部品 | GUI固有の取得コード（存在させない） |
| 保存済み数表だけを処理するツール | 読み取り、加工、保存・出力のフロー | ブラウザと検索部品は導入不要 |
| 独自画面・名称のアプリ | GUI、配布マニフェスト、初期設定 | 部品を呼ぶ共通契約 |
| 標準以外の処理種別 | 新しい契約・スキーマと実装の登録 | コアの処理種類の列挙や個別分岐 |

使いたいフローに必要な契約は満たす。何も導入しなくても検索ができる、という意味ではない。不要な部品を抱えずに済むことと、必要な部品の不足を黙って補うことは別である。

## 3. 基本の開発手順

1. 参考フローを複製し、独自のID・設定を付ける。標準フローをコアのコードとしてコピーしない。
2. 必要な操作の契約と入出力を決め、登録済み実装を選ぶ。不要なノードを外し、接続型を検証する。
3. 実装がなければ公開契約に従う部品を作る。新しい処理なら新しい型・操作スキーマを登録する。
4. モックを使い、GUIなしで順序・中断・再試行・結果参照を検証する。その後に実処理を接続する。
5. 同じAPIを呼ぶGUI／CLIを作り、選ぶ部品・版・初期フローを配布構成に記録する。

これらの設定変更や部品追加で済む範囲では、コアのフォークを必須にしない。フロー実行モデル自体を変更したい場合にコアを改変することは可能だが、部品の機能追加とは区別する。

## 4. 構成の置き場所の案

```text
packages/
  core/          フロー実行。処理の具体実装を参照しない
  contracts/     共通メッセージ、型・操作スキーマ
  host/          部品の登録・配送、実行環境のアダプター
clients/
  gui/           表示とAPI呼び出し
  cli/           同じAPIを呼ぶ別の入口
components/
  ...            ブラウザ・検索・取得・保存・加工などの独立実装
flows/
  ...            標準例と利用者が作るフロー
 distributions/
  ...            採用部品・版・画面・初期フローの組み合わせ
```

これは配置案で、現在のリポジトリにこの実装があるという意味ではない。同じモノレポか複数リポジトリかは未決定。依存方向が重要で、同じフォルダー階層にあることをコアへの組み込みと同義にしない。

配布定義は採用部品と固定版、初期フロー、GUI／CLI、必要設定、依存関係を指定する。標準部品のIDをコア内の既定値に埋めず、配布定義から渡す。開発元の登録サーバーや公式サービスへの接続を、派生ソフトの成立条件にしない。

## 5. 小さな例から交換可能性を確認する

[site-search.json](examples/site-search.json)は検索・取得・保存・出力の参考構成。[site-search-with-extensions.json](examples/site-search-with-extensions.json)は同じFlowConfigに入力支援と選別を加えた構成。

[local-processing.json](examples/local-processing.json)はWebやブラウザを使わない文字列処理のモック例。同じコアが呼び出せることを試し、Web関連の名前や型がコアの必須条件でないことを確認する。

全て説明用の仮実装IDであり、実行可能なプラグインが配布済みではない。交換試験では、操作・入出力・停止などの契約を満たす代替実装を用意する。

## 6. コアへ処理を入れないためのレビュー

新機能の説明にサイト名、ブラウザSDK、画像、数表、選別基準、出力形式が出る場合は、具体的な実処理として部品に置く。

処理を高速化したい場合も、部品やホストの呼び出し方式を改善する。標準部品だけを直接呼ぶ近道をコアやGUIへ作らない。同一プロセス実行を選ぶ場合でも、公開契約と差し替え可能性を維持する。

認証・通信輸送・プロセス管理・永続化など実行環境の具体方式はホストのアダプター等へ分離する。コアが保持するのは必要な抽象契約とフロー上の状態であり、特定OS・サービス・保存形式の実装ではない。

参照切れ、型不一致、未完了操作を検出することはフロー実行の正しさであって、内容の採否を決める機能ではない。この区別を保つ。

## 7. 派生構成と互換性

部品APIの互換性と、保存ファイルの互換性は別。保存部品の変更には移行やリーダーが必要な場合がある。設定版、部品契約版、実装版、モデル版、データ形式版を別々に記録する。

上流の更新でフローを壊さないため、使った版と設定を固定する。標準品の更新だけを理由に独自構成を上書きしない。

改変・組み替えを主要な利用方法とすることと、すべての依存コードに同じ配布条件があることは別。本体のライセンスは未決定であり、採用するOSSやモデルの条件・表示事項は依存単位で確認する。ここでは具体的な権利許諾を追加しない。

## 8. 到達条件

標準GUIなし、標準ブラウザなし、標準検索なしの構成をそれぞれ試験できること。必要な代替部品を与えれば、コアの具体処理コードを追加せず動かせること。

利用者が作った新しい操作を登録し、標準の処理カテゴリ外でも呼べること。失敗や中断の扱いは同じ公開契約で確認する。

この文書から参照する例、契約説明、受入テストを更新し、「改変できるはず」とだけ書いて終わらせない。
