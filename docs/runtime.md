# ブラウザ・実行制御

[設計書一覧](README.md)

R12〜R15およびR20〜R22の実装案。具体的な状態名・数値・更新方式は案である。停止、再読み込み、開き直し、取得間隔は、フィルター未導入でも動く取得基盤とする。

## 1. 取得ジョブと追加処理

コアのジョブは検索・取得・記録を管理する。解析・選別は別の拡張処理として管理し、その完了をコアの取得完了条件にしない。

操作UI、コア、取得ブラウザを分離する。追加モデルやフィルターを使用する場合も別ワーカーで管理する。ブラウザ停止時の操作受付を、対象ページのJavaScriptに依存させない。

ブラウザセッションはID、接続部・版、ブラウザ、専用プロファイル参照、対象ジョブ、世代番号を持つ。本体が起動した`managed`と既存環境に接続する`attached`を区別し、初期案は`managed`を優先する。本体が所有しない通常利用のブラウザをまとめて終了しない。

ページ再読み込みはブラウザの終了・再起動と別操作である。Playwrightにも別の操作としてAPIがある。[参考 S2・S3](references.md#s2)

## 2. 操作

| 操作 | 対象と動作 |
| --- | --- |
| 停止 | 取得ジョブの新規投入を止め、実行中処理を中断し、保存状態を確定する |
| 再読み込み | 指定ページの操作を中断し、同じページを読み直す |
| ブラウザ開き直し | 指定した管理セッションを終了し、同じ設定で起動し直す |
| 再開 | 保存した完了記録と継続情報を使って取得を再開する |

いずれも取得済みデータを削除しない。再読み込みと開き直しは別ボタンとし、対象・影響範囲を示す。初期案は取得ジョブごとに管理セッションを分ける。

ブラウザを開き直してもジョブID、取得履歴、予算消費、再試行回数、待機時刻をリセットしない。

## 3. コアの状態と停止

| 状態 | 意味 |
| --- | --- |
| `draft` | 取得設定の編集中 |
| `ready` | 検索・取得に必要な設定を検証済み |
| `running` | 検索・取得・記録を実行中 |
| `waiting` | 取得間隔、相手側指定の待機、再試行待ち等 |
| `recovering` | ページまたはブラウザの復旧中 |
| `stopping` | 停止要求を受けて処理を終了中 |
| `stopped` | 管理処理の終了と保存状態を確認済み |
| `needs_attention` | 認証要求、復旧失敗、取得方式非対応等への操作が必要 |
| `completed` | 取得処理が終了し、結果の保存状態を確定済み |
| `failed` | 取得ジョブを続行できないエラー |

`completed`には`target_reached`、`sources_exhausted`、`budget_exhausted`等の終了理由を付ける。予算上限で終了したことと、希望件数を取得したことを区別する。

解析・選別が存在しなくても`completed`になれる。後から追加フィルターが失敗しても、確定済みのコアの完了状態を失敗に書き換えない。ワークフロー全体の状態は別に示す。

停止時は新規投入、未開始の予約、自動復旧を取り消し、対象ワーカーへ中断を要求する。応答しない管理ワーカーは猶予後に終了する。停止操作の連打は同じ要求として処理する。

処理がまだ動いていれば`stopping`を表示し、終了を確認できない場合に`stopped`と偽らない。停止要求は復旧より優先する。中断した取得ファイルは一時ファイルとして分け、完成したデータにしない。

拡張機能を含む画面の「すべて停止」は、ホストが取得ジョブと拡張処理へ別々に停止を送る合成操作にする。コアが選別処理の型や結果を知る必要はない。

## 4. 再読み込み

対象ページへの投入を止め、操作を中断し、継続位置を記録してから再読み込みを要求する。アダプターが宣言する結果要素の存在等で準備完了を確認する。通信が完全に静かになることだけを全サイト共通の完了条件にしない。

古いページ要素の参照は再使用せず取り直す。完了済み操作を二重登録しない。新たな発見は出典として記録する。

タイムアウトした場合は利用者への確認待ちとし、開き直しを選べるようにする。自動復旧が有効な場合だけ、設定された次の処理へ進む。

## 5. ブラウザ開き直し

管理セッションへの投入を止め、継続情報をチェックポイントに保存する。接続部へ終了を要求し、応答しなければ所有する子プロセスを期限付きで終了する。

同じ接続部・ブラウザ・プロファイルで新しい世代のセッションを起動する。別のブラウザや検索サービスへ無断で切り替えない。

旧世代から遅れて届く結果は操作IDと世代番号で識別する。中断済み操作の結果を新しい状態へ混ぜず、すでに確定済みの結果は取り消さない。

継続位置を復元できなければ表示し、既知候補を参照しながら再探索する方法を選べるようにする。ブラウザ上の完全な状態復元は保証しない。

クッキー等はユーザーが選んだ専用プロファイルで管理する。通常利用のプロファイルを無断コピーしない。ログイン期限切れと停止を区別し、副作用のある購入・投稿などを再起動後に自動再送する設計にはしない。

## 6. 自動復旧

`manual`と`automatic`を用意する案とし、初期値案は`manual`。自動モードでは停止検知、再読み込み回数、開き直し回数、復旧間隔、復旧後の再開を設定する。

ページ応答タイムアウト、プロセス切断、アダプターエラーを区別する。間隔待ちや別の拡張処理の遅さを、ブラウザ停止と誤認しない。無限リロード・無限再起動は行わない。

## 7. 画像取得の時間間隔

### 7.1 ユーザー設定

画像取得、検索要求、ページ移動・再読み込みの最小間隔を別に設定できる。全体・掲載サイトの論理グループ・実接続先ごとの制約、同時数、時間窓の件数上限、タイムアウト、再試行も設定対象にする。

秒・ミリ秒の単位を明示し、画像取得間隔を詳細設定の中でも見つけやすくする。プロファイルで隠したり、任意フィルターの導入条件にしたりしない。

例の数値は試験用であり、相手サイトの取得・利用条件への適合を保証しない。間隔を長くするだけで、禁止された大量取得が許可されるわけではない。

### 7.2 間隔の意味

基本案は取得開始時刻間の最小間隔。5秒なら同じ制御グループの次の開始を5秒より前にしない。進行中の数も同時上限内でなければならない。

必要なら前の取得完了からの待機方式を追加し、対象グループの同時数1と組み合わせる。開始間隔と混同しない。

ワーカーごとに独立した待機を置くだけにせず、同一コア内のジョブ・タブ・ブラウザ間でサイト／接続先の制御状態を共有する。複数アプリインスタンス・端末間の協調は初期範囲外と明示する。

掲載サイトと画像CDNが別の場合は両方の制約を確認する。CDNの数が増えただけで掲載サイトの予算を分散・回避しない。

### 7.3 次に実行できる時刻

全体、サイトグループ、接続先、時間窓上限、相手側待機、再試行バックオフの各期限の最大値以降に、同時数と予算も満たした要求を投入する。

検索語追加、ブラウザ開き直し、ジョブ再開によって待機を消さない。コア再起動後にも復元する。プロセス内の間隔には単調増加時計を使い、永続化用時刻も持つ。時計変更等で不明なら待機または確認待ちにする。

### 7.4 相手側の制限

HTTP 429は過剰な要求の応答で、Retry-Afterを含む場合がある。Retry-Afterは秒数またはHTTP日付で表される。[参考 S6・S7](references.md#s6)

解析可能な待機期限より前に再試行しない。期限がジョブの許容時間を超えれば、待機を切り詰めず停止・保留とする。不正値や指定なしでは設定された有限回のバックオフを用いる。

認証要求、アクセス拒否、CAPTCHAを無限の一時エラー再試行にしない。復旧はアクセス制限回避に使う処理ではない。他の選択済みサイトを続けるかは設定できる。

### 7.5 保存間隔と通信間隔

ブラウザが表示時に先読みした画像を、保存時に待つだけでは通信頻度を下げられない。基本設定はコアが投入する要求を制御し、接続部が`dispatch_only`や`asset_requests`等の制御範囲を宣言する。

必要な制御に未対応なら表示し、方式変更・警告・実行保留を選べるようにする。全付随通信を制御できない方式で「すべての画像通信を制御」と表示しない。Playwrightの要求監視・ルーティングにもService Worker等の制約があるため、能力を実測する。[参考 S4](references.md#s4)

## 8. 実行中の変更

検索語・検索先は版を残し、初期案では停止後の次の実行に適用する。取得間隔・同時数・自動復旧等は`runtime_revision`で更新できる案とする。

受理後の未開始タスクから適用し、予約を再計算する。進行中要求を過去に遡って取り消さない。短い間隔に変更しても相手側の待機を解除しない。同時数を減らしたときは処理終了を待ち、新規投入を控える。

変更の旧値・新値・時刻・適用境界を記録する。初期実装を停止後変更に限るなら、その動作をUIとAPIで明示する。

追加フィルターの閾値変更は拡張側の選別版を作る。コアの取得設定変更や、再検索を自動的に発生させない。

## 9. 均等配分・豊富さ優先

既定は選択したサイト／検索先へ均等な探索枠を配る。サイト間、その内部のエンジン間など階層・重みを詳細設定にする。待機中の枠を保持するか他の選択済み検索先へ配るかも選べる。

探索機会の均等と、最終件数の一致は別である。結果数・失敗・重複によって差があることを表示する。

豊富さ優先は探索ページ、候補予算、出典の広がり等の詳細値に展開する。検索語展開支援を使う場合も追加機能として表示する。取得間隔を無断短縮せず、未定義の品質判定器を必須化しない。

プロファイルの差分を表示し、手動固定値と自動設定の優先方式を守る。

## 10. 件数・予算・再開

コアの目標は`discovered`、`downloaded`、`downloaded_unique`等の取得上の計数とする。初期案は`downloaded_unique`。ハッシュ一致による計数・保存共有は、意味に基づく近似重複選別とは別である。

`selected`をコアの完了条件にはしない。選別後件数まで追加収集する機能は拡張ワークフローが選択済みの条件・共有予算の範囲で別の取得要求を出す機能とし、明示的に設定した場合だけ実行する。

目標とは別に要求数、ページ数、転送量、単体サイズ、経過時間、容量、再試行の上限を管理する。失敗要求も消費に含め、再開でリセットしない。

並列処理で目標を超えた完了分は勝手に捨てず追加取得分として表示する。厳密な通信予算は開始前の予約と転送中計測で制御する。

チェックポイントには継続情報、候補ID、完了・中断、予算、待機期限、設定版を持たせる。モデル・フィルター・選別テーブル・残存タブを再開の必須条件にしない。

## 11. 追加機能が失敗した場合

使用していない拡張の不足はコアのエラーにしない。使用を指定した検索前の拡張が不足する場合は、ワークフローの開始前に不足を示す。ユーザーの指示を黙って無視して同じワークフローを続けない。

取得後の拡張エラーは、その拡張処理の失敗として保存する。取得データは閲覧・直接出力可能なままとし、コアの完了を取り消さない。

取得と解析が並行する場合は、拡張ホスト側で有限キューと読み取り位置を管理する。解析の遅延だけでコアを停止させるのではなく、取得データを記録して後から追いつけるようにする。利用者がワークフロー単位の停止を指定した場合は、その操作として別に記録する。
