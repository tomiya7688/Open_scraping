# ブラウザ・実行制御

[設計書一覧](README.md)

本書はR12〜R15を中心とした実装案である。再読み込み、開き直し、取得間隔のユーザー設定は確定要件。具体的な状態名、数値、更新方式は実装案とする。

## 1. ブラウザが停止しても操作できる構成

操作UI、ジョブ管理、取得ブラウザ、画像解析ワーカーを分離する。再読み込みボタンや停止ボタンの受付を、操作対象ページ上のJavaScriptに依存させない。

ブラウザセッションには `session_id`、接続部ID／バージョン、使用ブラウザ、プロファイル参照、管理方式、対象ジョブ、セッション世代を持たせる。

管理方式は本体が起動した `managed` と、既存環境への接続である `attached` を区別する。初期実装は `managed` を優先する。将来の `attached` では、本体が所有していないブラウザや通常利用のタブをまとめて終了しない。

Playwrightの `page.reload()` は現在のページを再読み込みする操作である。ブラウザの起動・終了とは別操作なので、接続部のAPIでも分ける。[参考 S2・S3](references.md#s2)

## 2. ユーザー操作

| 操作 | 対象 | 動作 | 保存済みデータ |
| --- | --- | --- | --- |
| 停止 | ジョブ | 新規投入停止、実行中処理の中断要求、保存状態の確定 | 残す |
| 再読み込み | 指定ページ | ページ操作を中断して同じページを読み直す | 残す |
| ブラウザ開き直し | 指定セッション | 管理ブラウザを終了して同じ設定で起動し直す | 残す |
| 再開 | 停止／保留中のジョブ | 保存した完了記録・継続情報から処理を再開する | 再利用する |

再読み込みと開き直しは別ボタンにし、対象ページ／セッション名を表示する。複数ジョブが同じセッションを共有する構成では影響範囲を表示する。初期実装案はジョブごとに管理セッションを分ける。

単なるブラウザ再起動では、本体のジョブID、出典情報、取得上限の消費量、再試行回数、スケジューラーの待機状態をリセットしない。

## 3. 状態と停止

### 3.1 ジョブの状態

| 状態 | 意味 |
| --- | --- |
| `draft` | 設定の編集中 |
| `ready` | 設定検証済みで開始可能 |
| `running` | 検索・取得・解析などを実行している |
| `waiting` | 取得間隔、相手側指定の待機、再試行待ちなど |
| `recovering` | ページまたはブラウザの復旧処理中 |
| `stopping` | 停止要求を受け、処理を終了させている |
| `stopped` | 実行処理の終了と保存状態を確認できた |
| `needs_attention` | 認証要求、復旧失敗、取得方式非対応など、利用者の操作が必要 |
| `completed` | 指定条件による処理の終了 |
| `failed` | ジョブを続行できないエラー |

`completed`には `target_reached`、`sources_exhausted`、`budget_exhausted` などの終了理由を付ける。予算上限に達しただけで、希望件数を満たしたとは表示しない。

### 3.2 停止手順

コアは新規投入を止め、待機中の予約と自動復旧を取り消し、全ワーカーへ中断要求を送る。既に完了した結果だけを保存済みとして確定する。

中断への応答がないワーカーは、設定された猶予後に本体の管理対象プロセスだけを終了する。停止ボタンの連打は同じ停止要求として処理し、プロセスを増やさない。

ワーカーが動作している間は `stopping` を表示する。OS側の問題等で終了を確認できないときは、その事実を表示し、`stopped`と偽らない。停止要求は復旧要求より優先する。

ダウンロード中のファイルは一時ファイルとして分離する。中断されたファイルを完成した画像として登録しない。停止しても元データを削除せず、完全削除は別の操作とする。

## 4. ページの再読み込み

対象ページへの新しい操作投入を止め、実行中のページ操作をキャンセルし、継続位置を記録する。ページ再読み込みを要求し、応答があればアダプターの準備完了条件を確認する。

準備完了条件はページ表示、必要な結果要素の存在などをアダプターが宣言する。ネットワーク通信が完全に静かになることだけを全サイト共通の完了条件にしない。

復旧後はページ要素への古い参照を再利用せず、必要な要素を取り直す。既に確定済みのデータを再採用したことにせず、再発見として出典情報へ追加する。

タイムアウトした場合は `needs_attention` とし、ブラウザ開き直しを選べるようにする。自動復旧が明示的に有効な場合だけ、設定された次の処理へ進む。

## 5. ブラウザの開き直し

管理対象セッションへの投入を止め、ジョブとページ送りの継続情報をチェックポイントに保存する。接続部へ終了を要求し、応答しない場合は所有している子プロセスを期限付きで終了する。

新しいセッション世代で同じブラウザ接続部・プロファイル設定を使って起動し直す。別のブラウザや検索サービスへ無断で変更しない。

旧セッションから遅れて届く結果は、操作IDと世代番号で識別する。中断済み操作からの遅延結果を新しいジョブ状態へ混ぜない。既にコミット済みの結果は取り消さない。

検索カーソルやページ位置を復元できる場合は続きから再開する。再現不能ならその旨を表示し、既知の候補ID・ファイルハッシュを使いながら先頭から再探索する方法を選べるようにする。ブラウザ上の完全な状態復元は保証しない。

クッキー等の保存はユーザーが選んだ専用プロファイルに限る。通常利用のプロファイルの無断コピーは行わない。セッション期限切れやログイン要求は復旧失敗とは分ける。購入・投稿等の副作用を持つ操作を再起動後に自動再送する設計にはしない。

## 6. 自動復旧の設定

実装案では `manual` と `automatic` を用意し、初期値は `manual` とする。自動モードでは、停止検知条件、ページ再読み込み回数、ブラウザ再起動回数、復旧間隔、復旧後の自動再開を設定できる。

応答タイムアウト、プロセス切断、アダプターエラーを区別する。取得間隔の待機中や長時間のモデル処理中であることを、ブラウザ停止と誤認しない。無限リロード・無限再起動は行わない。

## 7. 画像取得の時間間隔

### 7.1 設定できるもの

| 設定 | 意味 |
| --- | --- |
| 画像取得の最小間隔 | データセット用の画像取得を開始する間隔 |
| 検索要求の最小間隔 | 検索、検索の次ページ、検索語の追加問い合わせの間隔 |
| ページを開く最小間隔 | 掲載ページを開く、再読み込みするなどの間隔 |
| 全体／サイト別／接続先別の上限 | 複数の制約を同時に適用するための設定 |
| 同時実行数 | 間隔とは別に、進行中の取得数を制限する |
| 時間窓ごとの件数上限 | 例：指定した時間内の要求数。数値はユーザー指定 |
| タイムアウト・再試行 | 取得待ち時間、回数、再試行時の追加待機 |

秒・ミリ秒などの単位を明記する。UIでは画像取得間隔を見つけやすくし、プロファイルだけに隠さない。

設定例の数値は試験用の仮値であり、どのサイトでも安全・適法・許可済みの速度を意味しない。画像取得間隔を長くしただけで、禁止された大量取得が許可されるわけではない。利用者が相手サイトの条件を確認して設定する。

### 7.2 間隔の意味を固定する

基本の実装案は開始時刻間の最小間隔とする。例えば同じ制御グループ内で5秒の場合、0秒で開始した次の取得を5秒より前に開始しない。前の取得が終わっていなくても、同時数上限も満たす必要がある。

必要なら「前の取得完了からの待機時間」を別方式として追加する。その方式は対象グループの同時数1と組み合わせ、開始間隔と混同しない。

並列ワーカーごとに独立した待機だけを実装しない。同一のコアが動かすジョブ・ブラウザをまたいで、該当するサイト／接続先の制御状態を共有する。複数アプリインスタンスや複数端末の自動協調は初期範囲外であることを表示する。

掲載サイトと画像CDNが異なる場合は、掲載サイト側の論理グループと実際の接続先の制約を両方確認する。多数のCDNに分かれるだけでサイト側の取得予算を分散・回避しない。

### 7.3 次に実行可能な時刻

開始時刻方式では、次に投入可能な時刻は概念的に以下の最大値で求める。

```text
全体の次回時刻
サイトグループの次回時刻
実際の接続先の次回時刻
時間窓上限が回復する時刻
相手側が指定した再試行可能時刻
失敗後のバックオフ終了時刻
```

同時数・全体予算も満たした場合だけ投入する。検索語を追加する、ブラウザを開き直す、ジョブを再開することによって待機状態を消さない。コア再起動でも必要な待機状態を復元する。

同じプロセス内では単調増加時計で間隔を測り、永続化には時刻情報も保存する。時計の大きな変更などで経過時間が信用できない場合は、安全側に待機するか確認待ちにする。

### 7.4 相手側の制限と失敗

HTTP 429は過剰な要求に対する応答であり、`Retry-After`を含む場合がある。`Retry-After`は秒数またはHTTP日付で表現される。[参考 S6・S7](references.md#s6)

この設計では、解析可能な相手側待機時刻より前に再試行しない。待機がジョブの許容時間を超える場合は、待機時間を切り詰めて再送せず停止・保留にする。値がない／不正な場合は、設定済みの有限回のバックオフを使う。

アクセス拒否、認証要求、CAPTCHAなどを、通常の一時的な通信失敗と同じ無限再試行にしない。復旧操作をアクセス制限回避の処理にはしない。個別サイトの失敗時に他の選択済みサイトを続けるかは設定可能にする。

### 7.5 ブラウザの付随通信との区別

「画像を5秒間隔で保存する」と「ブラウザが行うすべての画像通信を5秒間隔にする」は異なる。表示のためにブラウザが先に取得した画像は、保存前の待機だけではアクセスを間引けない。

基本設定が制御するのは本体が投入する検索・ページ移動・データ取得である。接続部は制御対象を `dispatch_only`、`asset_requests` などの能力情報で示す。必要な画像通信制御をサポートしない方式で、「すべての画像アクセスを制御できる」と表示しない。

厳密な要求間隔が必要なサイトでは、要求を制御できる取得方式を選ぶ。ページ表示のための先読みや第三者通信まで完全に制御できない場合は、警告・方式変更・実行保留を選べるようにする。Playwrightには要求の監視・ルーティング機能があるが、Service Worker等による制約もあるため、能力は実測する。[参考 S4](references.md#s4)

## 8. 実行中の設定変更

実装案として、検索語や選別条件の変更は新しい設定版を作り、停止後の次の実行から使う。取得間隔・同時数・自動復旧の有効化などの実行制御は、別の `runtime_revision` で扱う。

間隔変更は、変更要求が受理された後の未開始タスクから適用する。既に開始した要求を過去に遡って取り消さない。予約済みだが未開始のタスクは再計算する。

間隔を短くしても、相手側の待機期限は解除しない。同時数を減らした場合、実行中処理の終了を待ち、上限内になるまで新しく投入しない。変更時刻・旧値・新値・適用境界を記録する。

この実行中変更は操作性のための提案であり、最初の実装を停止後変更に限定する場合でも、どちらの動作かをAPIとUIで明示する。

## 9. 均等配分とデータの豊富さ

既定の配分は、選択したサイト／検索先に均等な探索枠を割り当てる。サイト指定ではまずサイト間、必要ならその内部でエンジン間を配分する。階層や重みは詳細設定にする。

各検索先の要求ごとの結果数は異なるため、均等な探索機会と最終取得件数の一致は別である。待機している検索先の枠を保持するか、選択済みの別の検索先に振り替えるかを設定できる。

「データの豊富さ優先」は検索語の展開数、探索ページ、候補予算、出典の広がりなどの詳細設定に展開する。取得間隔を無断で短くする設定ではない。独立した複数指標を表示し、未定義の品質スコアで勝手にソースを選ばない。

プロファイル適用時は変更される値を示す。手動固定した時間間隔、サイト、ドメイン、上限を上書きする場合は、ユーザーが選んだ優先方式に従う。

## 10. 件数・予算・再開

目標は `discovered`、`downloaded_unique`、`selected` などを区別する。初期案はユニークな取得成功件数を使う。選別後件数まで追加収集する機能は明示的なオプションにし、後処理の変更だけで自動的にWeb通信を始めない。

目標件数とは別に、検索要求数、巡回数、転送量、単体ファイルサイズ、経過時間、ディスク容量、再試行回数を制限する。失敗した要求も消費量に含め、再開でリセットしない。

目標ちょうどの件数を超える可能性がある並列実行では、未開始タスクを止め、既に完了した余剰データは削除せず追加取得分として表示する。厳密なネットワーク予算は開始前の予約と転送中の計測で制御する。

チェックポイントには検索ごとの継続情報、候補ID、完了／中断状態、予算消費、待機期限、設定版を記録する。ブラウザのタブが残っていることを再開条件にしない。
