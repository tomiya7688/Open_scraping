# フロー実行とブラウザ復旧

[設計書一覧](README.md)

状態名・数値・実装方式は案。停止・再読み込み・開き直し・画像取得間隔は維持し、コアと外部部品の担当を分ける。

## 1. 実行基盤の境界

| 処理 | コア／ホスト | 部品 |
| --- | --- | --- |
| 開始 | フロー順序に従って操作を呼ぶ | ブラウザ起動、検索、取得等の実処理 |
| 待機・並列 | 宣言された資源キーと時刻・数値の制御 | サイト・接続先・要求の意味を解釈して制御情報を申告 |
| 停止 | 新規投入停止、中断配送、終了確認 | 実通信・ブラウザ・モデル等を中断し状態を返す |
| 再読み込み | 対象操作の競合を調整し、要求を配送 | ページの実際のreloadと準備確認 |
| 開き直し | 状態・世代・未完了操作の管理 | 管理ブラウザを閉じ、同じ設定で開く |
| 記録 | フロー・ノード・操作の状態と参照 | 取得元、ファイル、数表、解析・選別の記録 |

GUIはこの公開操作を呼び、表示するだけ。検索・取得の再試行をGUI側のタイマーで実装しない。

## 2. フローの状態

状態の案はdraft、ready、running、waiting、recovering、stopping、stopped、needs_attention、completed、failed。

コアはノードと依存関係の成否からフローの状態を決める。ノード名がsearchやfilterだから特別な完了規則を適用しない。何を必須の終端とするか、失敗時に停止するか、独立分岐を続けるかはフロー定義に明記する。

保存が成功し、その後の必須選別が失敗した場合、フロー全体は失敗または確認待ちになり得るが、保存ノードの成功や実データを取り消さない。取得フローと後処理フローを別runにすれば、後処理失敗で過去runの完了状態を変えない。

設定にない失敗ノードを黙って省略し、全体成功にしない。候補枯渇、件数目標、予算消費などの理由は部品が結果として申告し、未達と成功を区別して表示する。

## 3. 停止

新しいノードとサブ要求の投入を止め、待機予約・自動復旧を止めて実行中操作に中断を送る。中断要求は冪等にし、ボタン連打で処理を増やさない。停止は復旧より優先。

部品は完了済み・未完了の結果を区別して返す。保存部品は一時ファイルと確定済みデータを分け、停止したことを削除と解釈しない。

応答しない管理ワーカーはホストが猶予後に終了できる構成を候補にする。別プロセスだけで完全なOS隔離があるとは言わない。利用者の通常ブラウザや所有していないプロセスを終了しない。

処理停止が未確認ならstopping等を維持し、停止済みと偽らない。リモートサービス側の処理や既に送信済み要求を取り消せない場合は、その範囲を表示する。

## 4. 再読み込み

ユーザーが指定したブラウザ部品・セッション・ページを対象にする。コアは関係する操作の新規投入を止め、ホストへreload要求を配送する。実際のページ操作は部品が行う。

ページの準備完了は部品・サイトアダプターの結果要素等で判断する。全サイトで通信停止だけを完了条件にしない。Playwrightにもページ再読み込み操作があるが、その呼び出しとサイトごとの復旧は別である。[S2](references.md#s2)

古いページ要素を再利用せず、操作IDと世代を更新する。取得完了記録を確認し、新しい発見元情報と二重コミットを区別する。

タイムアウトはneeds_attention等にし、自動復旧を選んだ場合だけ設定済みの次操作に進む。

## 5. ブラウザ開き直し

ブラウザ部品はmanaged（所有するブラウザ）とattached（既存環境への接続）を区別する。初期案はmanaged優先。reopenの可否と影響するセッション・ジョブを表示する。

コアは新規呼び出しを止め、各部品のチェックポイント参照を保存する。ブラウザ部品は対象を終了・起動し直す。起動処理やSDKはコアに置かない。[S3](references.md#s3)

同じ接続部・設定・専用プロファイルを使い、未指定の別ブラウザへ変更しない。旧世代から遅れて返る結果は区別し、未完了の旧操作を新状態へ混ぜない。

検索カーソル、保存結果、予算、次回可能時刻はコアと各部品のチェックポイントに維持する。ブラウザを開き直すだけで待機や消費をリセットしない。

完全なページ状態の復元は保証しない。復元不能なら表示し、既知の結果を照合しながら再探索する操作を選べるようにする。通常利用プロファイルを無断コピーせず、購入・投稿等の副作用を持つ操作を自動再送する設計にはしない。

## 6. 自動復旧

手動／自動を設定できる。初期値案は手動。自動の場合は検知条件、reload回数、reopen回数、待機、復旧後の再開を宣言する。

復旧ポリシーは対象の能力と操作を指定する。コア内のブラウザ名分岐ではなく、汎用の実行規則として呼ぶ。コア自体やブラウザを無限に再起動しない。

要求待ち、処理中、指定間隔の待機、ページ無応答を分ける。画像モデルが遅いだけでブラウザ停止と判定しない。使用部品がreload等を持たなければ、その操作は未対応と表示する。

## 7. 取得間隔と資源制御

### 7.1 画面とコア設定を分ける

ユーザーには画像取得間隔、検索間隔、ページ移動間隔、同時数、サイト別上限などを表示する。単位を明記し、画像取得間隔を目立つ項目にする。

プリセット／設定部品がそれらを汎用の資源ポリシーへ展開する。コアは`min_start_interval_ms`、同時数、時刻、資源キーを扱うだけで、画像やドメインを解析しない。

部品は実際のネットワーク要求を始める前に、必要な資源キーについて共有スケジューラーから実行許可を取得する。最上位のfetch呼び出しの間隔だけを制御して、内部で一斉取得する方式を間隔制御済みとは扱わない。

### 7.2 開始時刻と共有

基本案は開始時刻間の最小間隔。例えば5秒なら同じキーの次の開始を5秒より前にしない。完了後待機方式を提供する場合は明示し、同時数との意味を定義する。

同じコア内のジョブ・タブ・部品間で資源状態を共有する。掲載サイトと実接続先が異なるとき、部品は両方のキーを申告する。CDNごとに分散しただけでサイト側の制限が失われないようにする。

キーの正規化は通信部品の契約で共通化する。コアのリミッターはホスト名の部分一致を実装しない。別端末・独立アプリインスタンス間の協調は初期範囲外と明示する。

メタ検索部品等がブラウザ部品へ委譲する場合、実通信の担当が一度だけ許可を取得する。親が同じ枠を保持したまま子が再取得して停止するような二重制御を避け、委譲関係を契約に含める。

### 7.3 待機時刻

全体・サイト・接続先・時間窓・相手指定・バックオフの各期限の最大値以降に、同時数と残予算も満たした要求を許可する。

HTTP 429とRetry-Afterの読み取りは通信部品が行う。値は秒数またはHTTP日付であり、部品が共通のnot_before等へ変換して返す。[S6](references.md#s6) [S7](references.md#s7)

相手の待機期限を利用者の短い間隔で上書きしない。期限が実行上限を超える場合は保留・停止する。認証要求・アクセス拒否・CAPTCHAを無限の通信再試行にせず、復旧をアクセス制限回避の処理にしない。

起動・再開・ブラウザreopenで期限を消さない。間隔計測には単調増加時計、永続化には復元可能な時刻を用いる。時計変更で経過が信用できない場合は待機または確認待ちにする。

### 7.4 ブラウザの付随通信

画像を保存する間隔と、ブラウザが先読みする画像通信の間隔は別。ブラウザ／取得部品はdispatch_only、asset_requests等の制御範囲を宣言する。

厳密な制御が必要なのに部品が未対応なら、警告・方式変更・確認待ちを選べるようにする。Playwrightのネットワーク制御にもService Worker等の制約があるため実測する。[S4](references.md#s4)

取得間隔の設定だけでサイトの取得・利用が許可されることは保証しない。例の数値は説明用で、利用者が対象条件に合わせて調整する。

## 8. 予算と配分

均等な探索、検索先間の重み、豊富さ優先は配分・検索部品またはプリセットで定義する。コアは宣言した重み付き資源や処理回数を実行する。探索機会の均等と最終取得数の一致は別。

発見数、取得数、一意件数、採用数は該当部品が計数し、意味・出所を示す。コアが画像ハッシュや採否を自分で計算しない。

要求数・時間・容量・並列数等の予算は共有し、失敗・再開で消費をリセットしない。厳密な転送上限は通信部品で転送中も計測する。APIコストや外部通信など、観測できない量は保証対象外と明示する。

選別後件数まで集める動作は明示的な有限フローとして構成する。閾値を変えただけで無断に検索を始めない。並列処理で既に完了した余剰取得分は保存部品が区別して記録する。

## 9. 設定版・再開・バックプレッシャー

フロー版、実行ポリシー版、各部品設定版を記録する。初期案は処理内容の変更を停止後の新runで適用し、間隔・同時数は受理後の未開始要求から適用可能にする。

間隔変更で既に送信した要求を過去に遡って止めない。予約を再計算し、短縮しても相手の待機は守る。同時数を減らしたら完了を待って新規投入を控える。

データの本体をコア内に無制限に蓄積しない。部品が永続または期限付きの参照を出し、コアは有界キューを扱う。後処理が遅ければ保存済み参照を後から読めるようにする。永続化できない接続ではバックプレッシャーをかける。

部品の再実行に伴う重複副作用は操作ID等で検出・照合する。外部世界を含めたexactly-onceを宣言しない。期限切れ参照・失われたチェックポイントは明示し、無断で再取得しない。
