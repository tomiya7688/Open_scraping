# 公開API・プラグイン設計

[設計書一覧](README.md)

本書のAPI名、設定キー、バージョンは**実装案**である。公開済みエンドポイントやSDKが存在するという意味ではない。標準実装も第三者実装も同じ契約を使うことを確定要件とする。

## 1. 二種類の公開API

| API | 利用者 | 役割 |
| --- | --- | --- |
| コア操作API | 標準UI、CLI、外部クライアント | 設定、ジョブ、実行制御、結果、選別、出力の操作 |
| プラグインAPI | ブラウザ・検索・モデル・選別等の実装 | 実行能力の宣言と、処理要求・結果・中断の受け渡し |

API仕様を公開することと、ネットワーク上に無認証で公開することを区別する。初期案はローカル利用で、操作APIはループバックにバインドし認証する。任意のWebページからコア操作を呼べないよう、Origin等の検証も行う。外部公開は別の明示的な配置設定とする。

操作APIはOpenAPIで定義する案とする。設定やプラグインの入出力はJSON Schemaで検証する。これらは利用候補であり、採用する仕様バージョンは実装時に固定する。[参考 S8・S9](references.md#s8)

## 2. 設定の単位

`JobConfig`は以下を持つ。検索文の解釈結果と、実行結果を設定そのものに混ぜない。

| セクション | 内容 |
| --- | --- |
| `schema_version` | 設定形式のバージョン |
| `input` | 元の自然言語、データ種別 |
| `scope` | サイト内／サイト指定／広域、対象サイト・エンジン、初期リンク条件 |
| `sources` | この設定で参照するサイト定義、接続方法、必要な抽出設定 |
| `browser` | 接続部、ブラウザ種類、管理方式、表示、プロファイル参照 |
| `interpretation` | モデル、優先方式、自動適用範囲、項目別の上書き規則 |
| `query` | ユーザー編集可能な分解条件・検索語。解釈前は未設定を表せる |
| `search_filters` | 順序を持つ検索時フィルターのインスタンス |
| `post_filters` | 後処理フィルター、設定、有効状態 |
| `selection` | 判定の組み合わせ、未判定の扱い、手動訂正の扱い |
| `profile` | プロファイルID、展開された詳細値、手動変更の有無 |
| `allocation` | サイト／エンジン間の重み、均等配分、余剰枠の扱い |
| `limits` | 目標件数の意味、要求数、容量、経過時間などの上限 |
| `timing` | 画像・検索・ページ移動の間隔、グループ別設定、同時数 |
| `recovery` | 手動／自動復旧、回数、待機、復旧後の再開 |
| `storage` | 保存先参照、保存期限、元データと派生データの扱い |

[サイト内検索の設定例](examples/site-search.json)を参照。例のドメイン、ID、値は説明用で、実在する対応サイト・インストール済みモデル・完成したプラグインを示さない。

`null`、未指定、空配列、無効は別の意味を持つ。例えば空の許可リストを全許可へ変換しない。コア設定の不明なキーは警告または検証エラーにし、拡張データはプラグインの名前空間に入れる。

## 3. 設定の優先順位

`manual_first`、`auto_first`、`per_field`を用意する。優先順位は値の採用規則であり、無制限の権限付与ではない。

各設定値について、値、出所、変更時刻、設定版、ユーザー固定の有無を管理する。自動適用可能なフィールド一覧はユーザー設定として管理し、モデルの出力により変更しない。

プロファイルは詳細設定に展開する。どのフィールドが変わるかを差分として表示する。非対応のフィルター値、ブラウザ能力、検索条件を黙って捨てず、`requested`と`effective`を分ける。

実行開始時の有効設定をスナップショット化する。実行中の間隔変更等は `runtime_revision` と変更イベントで扱い、過去の要求に適用された設定を後から書き換えない。

## 4. コア操作APIの草案

HTTP形式は一つの実装案である。UIの専用処理だけで実現する機能を作らず、同じ操作をAPIから行えるようにする。

| メソッド・パス | 処理 |
| --- | --- |
| `GET /api/v0/capabilities` | 実装されている機能・対応データ種別の取得 |
| `GET /api/v0/plugins` | プラグインと利用可能状態の一覧 |
| `POST /api/v0/plugins` | 明示的な許可に基づく登録・インストール |
| `PATCH /api/v0/plugins/{id}` | アプリ全体での有効状態等の変更 |
| `DELETE /api/v0/plugins/{id}` | 実装の取り外し。過去の結果は削除しない |
| `GET /api/v0/sources` | 検索サイト・エンジンの一覧 |
| `POST /api/v0/sources` | サイト・エンジンの追加 |
| `PATCH /api/v0/sources/{id}` | サイト設定の編集 |
| `DELETE /api/v0/sources/{id}` | 今後の選択肢から取り外す。履歴は維持する |
| `POST /api/v0/interpretations` | 自然文の分解・検索計画案の作成。検索実行とは分離 |
| `POST /api/v0/configs/validate` | 設定形式・参照ID・能力・矛盾の検証 |
| `POST /api/v0/jobs` | ジョブの作成。自動開始しない |
| `GET /api/v0/jobs/{id}` | 状態、設定版、進捗、待機理由 |
| `PATCH /api/v0/jobs/{id}/config` | 編集可能な状態で新しい設定版を作成 |
| `POST /api/v0/jobs/{id}/start` | 開始 |
| `POST /api/v0/jobs/{id}/stop` | 停止要求 |
| `POST /api/v0/jobs/{id}/resume` | 再開 |
| `PATCH /api/v0/jobs/{id}/runtime` | 取得間隔などの実行制御の更新 |
| `POST /api/v0/jobs/{id}/browser/reload` | 指定ページの再読み込み |
| `POST /api/v0/jobs/{id}/browser/reopen` | 指定管理セッションの開き直し |
| `GET /api/v0/jobs/{id}/events` | 順序付きの状態・操作・結果イベント |
| `GET /api/v0/jobs/{id}/items` | カーソル方式で結果一覧を取得 |
| `POST /api/v0/jobs/{id}/selections` | 保存済みデータの解析／再選別 |
| `POST /api/v0/selections/{id}/overrides` | 項目ごとの手動採用・除外・保留 |
| `POST /api/v0/jobs/{id}/exports` | 選別版を指定して出力 |
| `GET /api/v0/operations/{id}` | 長時間操作の進捗・完了状態 |

0.xでは未実装の機能を能力一覧で示す。例えば `not_implemented` を返し、空の成功結果で隠さない。`v0`のURL案は製品バージョンと別管理とし、安定化時に互換性を定義する。

### 4.1 長時間操作

開始・再読み込み・開き直し・解析・出力などは、受理時に `operation_id` を返し、完了を別イベントで通知する。HTTPで受理されたことと、ブラウザが復旧したことを同義にしない。

再送可能な操作には `idempotency_key` を付ける。同一キーの同一要求は既存の操作を返し、違う内容での再利用は競合とする。設定更新には期待する設定版を付け、古い画面からの更新を無断で上書きしない。

API応答には `request_id` を含め、ログで追跡できるようにする。停止要求は繰り返し可能とし、復旧より優先する。

## 5. プラグインの種類

| 種類 | 主な処理契約の案 |
| --- | --- |
| `browser` | `capabilities`, `open`, `navigate`, `reload`, `close`, `reopen`, `cancel` |
| `search` | `capabilities`, `validate`, `search`, `next`, `cancel` |
| `interpreter` | `interpret`, `expand_queries`, `cancel` |
| `extractor` | `extract`, `checkpoint`, `cancel` |
| `analyzer` | `analyze`, `cancel` |
| `filter` | `evaluate`, `cancel` |
| `exporter` | `export`, `cancel` |

実際の通信方式は未決定。実装言語を限定しないため、シリアライズ可能な契約を基本とし、ブラウザの内部オブジェクトを他の実装に直接渡さない。

`analyzer`は特徴・スコアを計算し、`filter`は条件に基づく選択案を返す。計算済みスコアを利用できるフィルターは、閾値変更だけで再解析しない。

プラグインの処理段階は `query_transform`、`candidate_filter`、`post_analysis`、`selection` などとして明示する。検索前の除外と取得後の除外をUIでも区別する。

## 6. マニフェスト

各プラグインはID、名称、版、プラグインAPI互換範囲、種類、対応するデータ種別、設定スキーマ、依存モデル、必要な権限、能力、説明、既知の制限を宣言する。

ブラウザの能力には、表示付き起動、再読み込み、管理プロセス再起動、永続プロファイル、要求間隔の制御範囲などを含める。検索側にはサイト内検索、画像結果、次ページ、言語・期間等の対応設定を含める。

標準フィルターは精度が限定的な初期実装でもよいが、対応範囲と未検証範囲を明記する。内製であることだけを理由に有効固定にしない。

プラグインがない場合、明示的な依存関係が未解決であると表示する。ユーザーが外した選別プラグインを、非公開の同等処理に置き換えない。

## 7. 共通の入力と結果

共通実行コンテキストには `job_id`、`operation_id`、設定版、実行制御版、期限、中断トークン、読み取り可能データ参照、進捗出力先を渡す。

大きな画像・動画や認証情報をJSONのログへ直接埋め込まない。データは限定された参照、認証は秘密情報ストアのハンドルを渡す案とする。

結果は以下のように、処理状態とデータ上の判断を分離する。

```json
{
  "subject_id": "item-example-001",
  "status": "ok",
  "values": {
    "condition_similarity": 0.42
  },
  "suggestion": "exclude",
  "reason_codes": ["below_user_threshold"],
  "evidence_refs": ["analysis-example-001"],
  "plugin_id": "builtin.image-relevance",
  "plugin_version": "0.1.0-draft",
  "settings_revision": 3
}
```

上記は契約説明用であり、実モデルの実測値ではない。`status`は `ok`、`unknown`、`unsupported`、`error` 等を区別する。`suggestion`は `keep`、`exclude`、`review` または未設定を表す。

解析失敗を「Tシャツではない」と扱わない。関連度スコアは確率として校正済みとは限らず、異なるモデルの数値をそのまま比較しない。スコアの意味と推奨範囲はプラグインが宣言する。

候補結果には元の検索要求、検索先、候補URL、掲載URL、データURL、タイトル等と解決状態を持たせる。同じデータを複数回見つけたときは発見経路を失わない。

## 8. フィルターの組み合わせ

一覧の順序を設定可能にし、順序依存のある処理はその旨を宣言する。選別の論理はAND／ORや除外条件の集合として表し、各チェックボックスが何をするかを明示する。

フィルター未実行・無効、評価して一致、評価して不一致、未判定、エラーを分ける。未判定を採用・保留・除外のどれにするかは選別設定として記録する。初期案は保留である。

通常の後処理は新しい `selection_revision` を作る。元データの削除、別サイトへの転送、再検索を副作用として行わない。追加のWeb取得が必要なら別の許可されたジョブ操作にする。

## 9. 実行権限と隔離

インストール時に、外部通信、読み取り対象、書き込み先、外部モデル送信、必要な秘密情報参照を表示する。権限変更を伴う更新は再確認の対象とする。

初期案はプラグインを別プロセスで動かし、停止期限・メモリ・入力サイズ等を管理する。ただし別プロセスであることだけでOS権限が完全に隔離されたとは表示しない。具体的なサンドボックス方式はOS選定後に決める。

対応アダプターは本体のスケジューラーを通して取得を投入する。任意の外部コードに対する完全な通信間隔保証はしない。スケジューラーを利用しない実装は能力表示で区別する。

外部ページのテキストをユーザーの設定命令として実行しない。モデルから返ったURL・ファイル名・処理案も検証する。ローカルの秘密情報や通常利用ブラウザのデータを検索結果と一緒に出力しない。

## 10. エラーと互換性

代表的なエラー区分は `invalid_config`、`unsupported_capability`、`not_implemented`、`permission_required`、`authentication_required`、`rate_limited`、`browser_unresponsive`、`parse_failed`、`plugin_failed`、`cancelled` とする。

再試行の可否、再試行可能時刻、影響範囲、利用者向け説明を付ける。技術的失敗を選別上の不一致として記録しない。

製品、設定スキーマ、プラグインAPI、プラグイン、モデルの版は独立して記録する。モデルは名前だけでなく取得元・リビジョンやハッシュを残す案とする。

0.xでは変更を許容するが、破壊的変更は明記する。1.0.0前に互換範囲、移行、廃止予定の通知方式を確定する。実行中ジョブの依存プラグインを取り外す場合は停止か処理終了を要求し、使用中のコードを無言で差し替えない。
