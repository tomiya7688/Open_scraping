# 外部部品と標準配布

[設計書一覧](README.md)

改訂日：2026-09-22。部品名、契約名、操作名は設計案。採用・実装済みではない。

## 1. 「内製」の意味

内製は開発・保守の主体を示し、コアに実装するという意味ではない。標準同梱、公式、他者製、商用・非商用、ローカル・リモートは別の属性として管理する。

本プロジェクトが保守するブラウザや検索も、他の実装と同じ公開APIを提供する部品にする。独立したパッケージとして更新・交換でき、コアから特別な内部処理を直接呼ばない。

外部部品を必ず外部サーバーに置く必要はない。ローカルプロセス、別サービス、既存APIへのアダプター、必要なら同一プロセス内の実装も契約上は扱える。隔離・停止能力は別途表示する。

## 2. 内製ブラウザの初期範囲

**既存のオープンソースブラウザを基盤にし、必要な操作を本プロジェクトのAPIで呼べるようにする。** 描画エンジン、JavaScriptエンジン、一般ブラウザの全UIを自作する計画ではない。

提供する操作の案は起動、ページ作成・移動、状態取得、再読み込み、セッション開き直し、終了、キャンセル。プロファイル・ダウンロード委譲・要求制御等は能力として宣言する。

初期候補はChromiumまたはFirefox系と、Playwright等の制御実装を包むアダプター。ChromiumはOSSプロジェクトで、Playwrightは対応するブラウザ版を管理する。PlaywrightのFirefoxは専用の修正版で、通常配布版をそのまま操作するものではない。[S1](references.md#s1) [S12](references.md#s12)

コアがPlaywrightに依存するのではなく、ブラウザ部品がPlaywrightに依存する。上流版、ブラウザ版、アダプター版を個別に固定・記録する。

薄いアドレス欄や操作画面を付ける場合も、同じブラウザ部品APIを呼ぶ。GUIのボタンにPlaywrightの操作コードを直書きしない。GUIなしで同じ操作を使えるようにする。

検索成功を保証しない方針は維持する。起動・再読み込み等の契約試験と、特定サイトの検索結果が得られるかの試験を分ける。

## 3. 内製検索の初期範囲

**既存OSSの検索ソフトウェアを再利用し、検索要求と結果を共通APIで扱える部品を提供する。** 初期案はメタ検索・サイト検索を中心にし、Web全体の独自インデックスを必須にしない。

候補のSearXNGは検索APIを公開している。利用する出力形式はインスタンス側の設定にも依存するため、JSON等の利用可否を接続時に確認する。[S5](references.md#s5)

候補の組み合わせは「SearXNG＋共通APIアダプター」。SearXNGを必須依存にするのではなく、Google、DuckDuckGo、Bing、Yahoo、サイト内検索の部品などと同じ検索契約で選択する。上流が提供するAPIや検索結果を、本プロジェクトが独自に生成していると表示しない。

検索部品が複数エンジンを内部で使う場合、実問い合わせ先、選択設定、サブ要求の進捗・消費を公開する。上位フローと内部メタ検索の二重実行や、二重の均等配分を起こさないよう担当層を設定する。

後から独自インデックス検索を追加しても、同じ検索契約の別部品で表現する。コアに検索のランキングやインデックス処理を追加しない。

## 4. 公開する部品契約の案

| 契約 | 実処理の責務 | 操作例 |
| --- | --- | --- |
| `browser.session/v1` | ブラウザの制御・プロファイル・復旧 | open, navigate, reload, reopen, close |
| `query.interpreter/v1` | 意図分解、検索語・条件の提案 | interpret |
| `search.provider/v1` | 検索、サイト定義、ページ送り、候補列挙 | search, next, validate_source |
| `candidate.filter/v1` | 検索結果・初期リンクの条件評価 | apply |
| `download.provider/v1` | データの取得、再試行情報、取得来歴 | fetch |
| `download.filter/v1` | 取得前メタデータ／取得直後データの評価 | apply |
| `data.process/v1` | 本文・表の抽出、変換、特徴・タグ・スコア計算 | process |
| `data.select/v1` | 条件の組合せ、採用・除外・保留の結果 | select |
| `dataset.store/v1` | 本体・出典・解析等の保存、一覧、スナップショット | ingest, list, snapshot, read |
| `dataset.export/v1` | ファイル・CSV・JSONL・ZIP等への出力 | export |

型、操作、エラー、停止、進捗、データ参照の共通部分を固定する。部品固有の設定はマニフェストのスキーマで公開し、コアにベンダー別の設定分岐を書かない。

「検索フィルター」「ダウンロードフィルター」「後処理フィルター」は画面上の段階を示す。取得前はURL・ヘッダー等、取得後は実データというように入力型と評価対象を明示する。取得していない内容を評価済みとしない。

単に通過させるだけのフィルターノードを必須挿入しない。フィルターのない接続も正規のフローとする。

## 5. 依存の注入

検索部品がブラウザを必要とするときは、「標準Chromiumの内部実装」ではなく`browser.session/v1`を要求する。利用者が選んだ実装をホストが束縛する。

部品が別部品を呼ぶ場合も登録した依存先を公開API経由で呼び、実行ID、キャンセル、待機、予算を共有する。UIや部品内で無断の検索サービス・ブラウザへ切り替えない。

依存先をコアの秘密の既定値で補完しない。標準配布のプリセットが選ぶ値と、利用者が固定した値を保存して表示する。

ブラウザを使わないAPI検索やHTTPダウンロードには、その能力を満たす限りブラウザ依存を要求しない。

## 6. インストールと互換性

マニフェストにID、版、提供契約と対応操作、設定・入出力スキーマ、依存契約、必要な権限、停止能力、実行環境、上流・ライセンス情報を持たせる。

契約名が同じだけでは全てのオプションが共通とは限らない。必須操作と任意能力を分け、未対応オプションを黙って捨てない。実行ごとに解決した実装・版・設定を固定する。

標準同梱は配布マニフェストで選択する。コアのimport、固定IDへの特例、標準品だけの非公開APIを設けない。標準品を別実装へ交換しても、コアとGUIの業務処理は修正不要であることを試験する。

ライセンス・通知・改変配布・商標等の扱いは採用する部品・版ごとに確認する。商用か非商用かだけで適否や配布条件を決めない。MozillaのMPL FAQも利用と再配布の条件を区別している。[S13](references.md#s13)

## 7. 取り外しと障害

取り外す部品が未使用なら、対象フローには影響しない。使用中なら該当する操作・依存先を表示し、停止・完了・設定変更を必要に応じて行う。

必要な検索・保存部品を取り外したフローを、そのまま実行できると保証しない。不足したノードの実行不能と、コアが壊れたことは別である。

保存部品が残る構成では、解析・選別部品を取り外しても元データを閲覧・出力できる。保存部品自体の交換にはデータ移行または互換リーダーが必要な場合がある。API互換と保存形式の互換を混同しない。

## 8. 配布物の見方

標準版は「GUI＋コア＋ホスト＋初期部品セット＋プリセット」である。コア単体版やCLI構成も可能にする。

1.0.0の三種類、1.1.0の動画対応は標準構成としての製品能力であり、コアに画像用・動画用の実装が増えることを意味しない。
