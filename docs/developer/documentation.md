# ドキュメント運用規則

[開発者向けトップ](README.md) · [利用者向けトップ](../user/README.md)

## 読者を先に決める

| 内容 | 正本の配置 |
| --- | --- |
| 使い始め方・現在できること・制限・用語 | `docs/user/` |
| 全体開発方針・参加手順・テスト・レビュー | `docs/developer/` |
| アーキテクチャ・契約・ADR・研究・実装ロードマップ | `docs/developer/` 配下 |
| 共通の JSON フロー定義例（現行の契約フィクスチャ） | `docs/examples/` |
| リポジトリ入口と実装状態の要約 | ルート `README.md` |
| 両方の読者を案内するナビゲーション | `docs/README.md` |
| 特定パッケージの公開面と入口 | `packages/*/README.md` 等 |

以前の `docs/*.md` および `docs/adr/` / `docs/research/` のパスは移行案内です。**本文の正本を2か所で編集しない**ようにします。既存リンクの訪問者を新しい正本へ案内する目的で維持します。

## 内容の品質

- **実装済み / テスト済み / PR提案中 / 設計のみ / 未実装** を明確に区別し、根拠のない「対応済み」「安全」を書かない。
- コードと一致する実行可能なコマンドを掲載する。導入前のAPIを実行例として紹介しない。
- 説明、サンプル、型・契約、エラーメッセージの変更は同期して更新する。
- バージョンとOSの保証範囲を記録する。現状確認は main のコミットや Issue/PR を根拠にする。
- フィルターやサイトの制約をCoreの固定機能のように説明しない。
- 外部リソースの出典・版・ライセンスや検証条件を必要に応じて記載する。

## 編集時のチェック

1. 影響する読者（利用者 / 開発者 / 両方）を選ぶ。
2. 正本ファイルだけを変更し、必要なら入口の `README.md`、索引、サンプルも調整する。
3. 相対リンクと実ファイルの存在を確認する。章への `#anchor` も人手で点検する（リンク検査は主に存在確認）。
4. `npm run check:docs` と必要に応じて `npm run verify` を実行する。
5. PRに「何が変わり、どの読者へ影響するか」を書く。

変更内容が未確定なら対応Issue/ADRを先に更新します。公開契約と設計原則の大幅な変更を文書だけで既成事実化しません。
